# Create Spec — спецификация в 3 слоя

## 📚 Объясни пользователю (перед началом, своими словами, 5–7 предложений)

Спецификация («спека») — письменный план продукта до начала кода: без неё ИИ молча заполняет
пробелы собственными решениями, и получается не то, что нужно, плюс бесконечные переделки.
Наша спека — три слоя, каждый отвечает на свой вопрос:

1. **Функциональные требования** — ЧТО продукт делает и для кого;
2. **Техническая архитектура** — НА ЧЁМ он собран, из каких компонентов;
3. **Девелоперская архитектура** — КАК его запускать и как ИИ проверяет сам себя.

Вместе они дают ИИ всё, чтобы собрать продукт без бесконечных переделок. Честная оговорка:
спека — под размер задачи, а не бюрократия ради бюрократии; каждый слой — компактный файл
в одну-полторы страницы.

## Твоя роль

Ты — дирижёр: ведёшь три этапа по очереди и держишь паузы между ними. Всю содержательную работу
(интервью, черновики, критику) делают этапные скиллы — **не дублируй их логику**.

## Порядок работы

```
- [ ] 0. Режим: новый проект или существующий (есть ли код) — сообщи пользователю
- [ ] 1. Учебный блок: что такое спека, 3 слоя = 3 вопроса
- [ ] 2. Слой 1: вызови скилл spec-requirements (передай идею из аргумента)
- [ ] 3. ПАУЗА — жди явного одобрения слоя 1
- [ ] 4. Слой 2: вызови скилл spec-architecture
- [ ] 5. ПАУЗА — жди явного одобрения слоя 2
- [ ] 6. Слой 3: вызови скилл spec-dev-architecture
- [ ] 7. Итог: обзор трёх файлов docs/spec/, что дальше
```

### 0. Режим

Посмотри, есть ли в проекте код (что угодно кроме `docs/`, `.claude/`, `CLAUDE.md`, README).
Есть → скажи пользователю: работаем в режиме существующего проекта — спеку будем восстанавливать
из кода («как есть») и уточнять у него «как хотим»; этапные скиллы сделают это сами.
Также проверь `docs/spec/` — если какие-то слои уже готовы, предложи продолжить со следующего,
а не начинать заново.

### 2–6. Три этапа с паузами

Вызывай этапные скиллы через Skill tool: `spec-requirements` → `spec-architecture` →
`spec-dev-architecture`. Каждый этап сам заканчивается жёсткой паузой — **уважай её**: никогда
не запускай следующий слой, пока пользователь явно не одобрил предыдущий («да», «дальше»,
«одобряю»). Захотел что-то поправить — сначала правка и подтверждение, потом следующий слой.

Между слоями — одна связующая фраза, зачем следующий слой (слой 1 сказал ЧТО строим → слой 2
выбирает, НА ЧЁМ → слой 3 договаривается, КАК ИИ будет сам проверять свою работу).

### 7. Итог

Когда все три файла готовы, покажи финальный обзор:

- `docs/spec/01-functional-requirements.md` — ЧТО и для кого: <одна строка сути>
- `docs/spec/02-tech-architecture.md` — НА ЧЁМ: <одна строка — главные компоненты>
- `docs/spec/03-dev-architecture.md` — КАК проверяем: <одна строка — петля>
- Открытые вопросы по всем слоям: <список или «нет»>

И что дальше по курсу: `/spec-user-flows` — развёртка спеки в экраны (какие экраны, в каком
порядке, что на них написано); затем `/setup-ui` — UI-кит и тема; затем `/build-screens` — сборка
экранов на заглушках. К любому слою можно вернуться его скиллом отдельно — например,
`/spec-architecture`, если передумали про стек.

Если в проекте уже есть план разработки (`docs/tasks/`), добавь строку: спека изменилась,
а задачи об этом не знают — предложи `/create-dev-plan`, он сверит план со спекой и поправит
задачи. Сам план в этой сессии не трогай.

## Правила

- Дирижируй, не дублируй: никакого интервью и черновиков в этом скилле — только этапами.
- Один этап за раз; следующий — только после явного одобрения.
- **Финальный отчёт — по общему формату** (`skills/_shared/report-format.md` этого плагина):
  первой строкой итог, детали — в документ, в конце — блок «Что делать дальше».
- Отвечай на языке пользователя; определять не по чему (скилл вызван без текста) — по умолчанию
  русский. Код и идентификаторы не переводятся.
