# Формат задачи разработки (общий файл)

Этот файл — общий контракт для всего этапа разработки. Его читают скиллы `create-dev-plan`,
`run-task`, `build-tasks` и агенты `implementer`, `task-verifier`. Здесь описано три вещи:
где живут задачи, как выглядит файл задачи и какого размера задача считается хорошей.

## Где живут задачи

```
docs/tasks/
  board.md            доска для человека — перегенерируется из файлов задач, руками не правится
  T01-<slug>.md       одна задача = один файл
  T02-<slug>.md
  artifacts/T01/      доказательства задачи — по папке на задачу: скриншоты, ответы API, выписки из базы
```

Один файл на задачу — не украшение: статус задачи меняется только в её собственном файле,
поэтому два агента не спорят за один документ, а вся история задачи лежит в одном месте.
Идентификаторы `T01`, `T02` … выдаются по порядку создания и никогда не переиспользуются.

`docs/tasks/` — часть документации проекта, коммитится вместе с кодом. Из артефактов
в git попадают **только текстовые** доказательства (логи, выписки из базы, json) —
это держит `.gitignore`; скриншоты и прочие бинарники остаются локальными. Поэтому ссылка
в журнале на скриншот может указывать на файл, которого в репозитории нет, — это норма,
а не ошибка: скриншот был нужен на приёмке здесь и сейчас, в истории остаётся текст.

## Файл задачи

```yaml
---
id: T07
type: feature                 # setup | feature | fix
status: todo                  # todo | in_progress | done | needs_human | cancelled
origin: spec                  # spec — из плана по спеке · adhoc — задача, поставленная текстом
phase: "Первая фича"          # к какой фазе плана относится (у adhoc — пусто)
blocked_by: [T03, T05]        # задачи, которые должны быть done раньше. [] если таких нет
traces_to: "01-functional-requirements.md#запуск-прогона · 04-user-flows.md#поток-2"
spec_sync: ok                 # ok — задача согласована со спекой · pending — спека ещё не догнала
summary: "Запуск прогона создаёт проект и списывает кредит"   # одна строка для доски
acceptance:                   # критерии приёмки — их доказывает тестировщик
  - "Дано пользователь с кредитами, Когда он нажимает «Запустить», Тогда в projects появляется строка со статусом analysis"
  - "Дано пользователь без кредитов, Когда он нажимает «Запустить», Тогда прогон не стартует и показан текст из потока"
verify_attempts: 0            # сколько раз задача уходила на проверку
review: human                 # заполняет run-task на приёмке: human — принял человек · auto — руками проверять было нечего
---

## Описание

Подробное задание для ИИ: что сделать, где это живёт в проекте, какие разделы спеки и потоков
относятся к делу, какие ограничения. Здесь можно писать столько, сколько нужно, — в отличие
от `summary`, который всегда одна строка.

## Журнал

Общий канал агентов, только дописывается снизу, старое не переписывается. Сюда пишут
исполнитель и тестировщик: что сделано, что найдено, чем доказано.

- 2026-07-20T12:31Z [implementer] Роут и списание кредита готовы, удачный сценарий проверил сам.
- 2026-07-20T12:45Z [task-verifier] Попытка 1, ПРОВАЛ: при нулевом балансе строка в projects всё
  равно создаётся. Доказательство: artifacts/T07/zero-balance.png + выписка из базы.
- 2026-07-20T13:05Z [task-verifier] Попытка 2, УСПЕХ: оба критерия доказаны (скриншот + строки в БД).
```

### Поля

| Поле | Правило |
|------|---------|
| `type` | `setup` — подготовка окружения и инструментов · `feature` — новое поведение продукта · `fix` — правка уже написанного кода |
| `status` | `todo` → `in_progress` → `done`; тупик — `needs_human`; снятая работа — `cancelled` |
| `origin` | `spec` — задача из плана по спеке · `adhoc` — задача, поставленная человеком текстом через `/run-task` |
| `blocked_by` | единственный способ задать порядок. Приоритетов нет: очередь диктуют зависимости |
| `traces_to` | откуда задача взялась в спеке. У задач `origin: spec` заполняется всегда: задача, которая не выводится из спеки, означает, что либо спека неполна, либо задача лишняя. У `adhoc` — прочерк, пока спека не догонит |
| `spec_sync` | `ok` — задача согласована со спекой · `pending` — задача меняет продукт, а спека этого ещё не описывает. `pending` — видимый долг: он показывается на доске и закрывается обновлением спеки, а не забывается |
| `summary` | одна строка человеческим языком, без жаргона — это то, что человек читает на доске |
| `acceptance` | проверяемые критерии «дано — когда — тогда». Пишутся **до** начала работы, иначе «готово» решает сам исполнитель |
| `verify_attempts` | увеличивает тестировщик на каждом круге; на втором круге задача уходит в `needs_human` |
| `review` | кто принял работу; решается **на этапе реализации**, не при планировании. На приёмке `run-task` смотрит фактический дифф и доказательства: человеку нечего проверять руками (весь дифф — тесты, конфиги, внутренняя логика; каждый критерий доказан автотестом, вся ручная проверка свелась бы к «запусти тесты сам») → ставит `auto` и принимает без вопроса; есть экран, тексты, видимое поведение, деньги, доступы, удаление данных → `human`, пауза с человеком. Сомнение = `human`. Если человек заранее вписал в файл задачи `review: human` — это приказ: автоприёмка запрещена |

### Статусы

```
todo ──> in_progress ──> done
             │
             └──> needs_human   (два круга проверки не помогли — нужен человек)
todo ──> cancelled              (работа больше не нужна)
```

- `done` — не «код написан», а «проверено тестировщиком и закоммичено».
- `needs_human` — штатный исход, а не авария: система говорит «здесь я упёрлась» вместо бесконечного
  хождения по кругу. Такая задача больше не берётся автоматически, её ждёт человек.
- Задача **готова к работе** (ready), когда её статус `todo` и все задачи из `blocked_by` — `done`.
  Из готовых берётся задача с наименьшим номером: так порядок повторяем и не зависит от настроения.

## board.md — доска

Простой markdown, который человек открывает и сразу видит состояние. Всегда перегенерируется
из файлов задач целиком, руками не правится:

```markdown
# Доска разработки

> Обновлено 2026-07-20 · 14 задач · готово 3 из 14
> Сверено со спекой: 2026-07-20 · коммит a1b2c3d

## ⚠ Нужен человек
- **T09** Письмо для сброса пароля — два круга проверки не помогли, подробности в задаче

## ⚠ Спека отстаёт
- **T12** Кнопка «Скачать в Word» — задача сделана, в спеке этой фичи ещё нет

## В работе
- **T07** Запуск прогона создаёт проект и списывает кредит

## Готовы к работе
- **T08** История проектов показывает настоящие проекты из базы

## Ждут
- **T10** Удаление проекта — ждёт T08

## Сделано
- **T01** Vitest и тесты в общей команде проверок · **T02** Таблицы и RLS

## Снято
- (нет)
```

Готовое в план не попадает вообще: задач со статусом `done` при первой генерации плана не бывает,
в плане только та работа, которую предстоит сделать.

Строка «Сверено со спекой» — якорь для сверки: дата и коммит, на котором план в последний раз
приводили в соответствие со спекой. По нему видно, менялась ли спека с тех пор
(`git log <коммит>..HEAD -- docs/spec/`), и не приходится гадать.

## Спека и план должны сходиться — в обе стороны

Спека описывает, каким продукт задуман; план — что для этого осталось сделать. Разъезжаются они
незаметно и в обе стороны, поэтому у каждой стороны есть свой ход.

**Спека изменилась → план догоняет.** Человек поправил требования, добавил фичу или переписал
поток — план об этом не знает и продолжает вести к старому продукту. Сверку делает
`/create-dev-plan`: он смотрит, что изменилось в спеке с последней сверки, и приводит задачи
в соответствие:

| Что случилось в спеке | Что делаем с планом |
|---|---|
| Появилась новая фича | новая задача |
| Фича изменилась, задача ещё `todo` | правим описание и критерии приёмки этой задачи |
| Фича изменилась, задача уже `done` | новая задача типа `fix` — сделанное не переписываем задним числом |
| Фича убрана из спеки, задача `todo` | `cancelled` — но только с подтверждения человека |
| Фича убрана из спеки, задача `done` | код остался в продукте: спрашиваем человека, нужна ли задача на удаление |

**Сделали то, чего нет в спеке → спека догоняет.** Человек попросил что-то текстом через
`/run-task`, работа сделана — но продукт теперь умеет больше, чем написано в спеке. Порядок здесь
обратный и намеренно нежёсткий: сначала работа, потом документ. Задача помечается `spec_sync: pending`,
после приёмки скилл предлагает донести изменение в спеку — в слой 1, если появилась или изменилась
фича, и в `04-user-flows.md`, если изменились экраны, состояния или тексты. Донесли — ставим
`spec_sync: ok` и заполняем `traces_to`.

Почему не наоборот, не «сначала спека»: человек приходит с задачей, когда ему нужна задача,
и требование сперва сходить в документ его просто остановит. А вот незакрытый долг видно на доске,
и он не теряется. Правило простое: **работу не блокируем, расхождение не замалчиваем**.

## Какого размера должна быть задача

Главный баланс этапа разработки. Слишком крупная задача не помещается в одну сессию — ИИ теряет
контекст и начинает путаться; слишком мелкая тонет в накладных расходах цикла, потому что на
каждую задачу приходится проверка, приёмка и коммит.

| Признак хорошей задачи | Что это значит |
|---|---|
| **Один присест** | Задача целиком делается за одну сессию агента. Не помещается — дели |
| **Вертикальный срез** | «Пользователь может X», а не «сделать таблицу в базе». Срез виден глазами и проверяется тестом, слой — нет |
| **Критерии до начала** | «Дано — когда — тогда» написаны заранее, иначе «готово» определит тот же, кто делал |
| **Привязка к спеке** | У задачи из плана всегда есть `traces_to` |
| **Явные зависимости** | Порядок задаёт `blocked_by`, а не ощущение важности |
| **Первая — самая тонкая** | Первой идёт задача, после которой продукт уже работает насквозь, пусть и в одном сценарии |

Примеры разного размера на этом проекте:

| Формулировка | Размер | Почему |
|---|---|---|
| «Сделай бэкенд сервиса» | слишком крупная | несколько дней работы, ни одного проверяемого критерия |
| «Прогон по запросу: создаётся проект, списывается кредит, статус виден на экране» | в самый раз | один сквозной срез, проверяется скриншотом и строкой в базе |
| «Создай таблицу projects» | слишком мелкая | слой без наблюдаемого поведения, проверить нечего — идёт частью соседней задачи |

Дробить задачу на подзадачи внутри файла не нужно: если работа не помещается в один присест,
это не одна задача с подпунктами, а две задачи со связью `blocked_by`.

## Сколько задач в плане: не больше 15

У размера есть и вторая граница, сверху: **в плане не больше 15 задач**. Снизу задачу держит
присест агента, сверху — это число, и вместе они задают крупность нарезки.

Почему именно потолок, а не «сколько получится». План на 40 задач выглядит подробным, но работает
хуже: человек перестаёт его читать целиком, порядок тонет в связях `blocked_by`, а на каждую
мелкую задачу всё равно тратится полный цикл — проверка, приёмка, коммит. Обычно такой план — это
не большой продукт, а мелко нарезанный: те же 12 задач, разложенные по слоям.

Что делать, если задач получается больше:

1. **Собери задачи одной фичи в одну.** Миграция, запрос, экран и текст ошибки — это один
   вертикальный срез, а не четыре задачи. Порядок внутри среза живёт в описании задачи, а не
   в отдельных задачах.
2. **Проверь, не попали ли в план слои.** «Создать таблицу», «добавить роут», «подключить клиент»
   отдельными задачами не бывают — они уходят частью соседней задачи.
3. **Всё равно больше 15** — значит, разрыв между спекой и кодом больше одного плана. Скажи это
   человеку прямо и предложи спланировать ближайшую часть: `/create-dev-plan <фича>` планирует
   одну фичу, остальное попадёт в план позже, при сверке. Молча выкатывать 30 задач нельзя.

Задачи в статусах `done` и `cancelled` в эти 15 не считаются: потолок — про работу впереди.

Потолок держит и жизнь после планирования: аудиты, `health-check` и adhoc-просьбы добавляют
задачи по одной, и доска расползается сама собой. Собирает её обратно скилл `/groom-tasks` —
сливает мелкие и однопричинные `todo`-задачи в связные крупные, не теряя ни одного критерия
приёмки.

## Чем задача закрывается

Задача переходит в `done` только когда выполнено всё:

1. тестировщик доказал **каждый** критерий приёмки наблюдаемым результатом — скриншот, строка
   в базе, ответ сервера («ошибок нет» и «код написан» доказательствами не считаются);
2. автопроверки проекта зелёные (мини-скилл проверок — линтер, типы, тесты);
3. человек принял работу — либо задача помечена `review: auto` (вся проверка автоматическая,
   смотреть глазами нечего), либо приёмка отложена его же явным решением (режим «приёмка раз
   в N задач» в `/build-tasks`). В обоих автослучаях в журнале — запись об автоприёмке,
   а ближайшая ручная приёмка показывает пакет автопринятых задач;
4. изменения закоммичены — один коммит на задачу, с номером задачи в сообщении.

## Язык

Файл задачи и записи в журнале пишутся на языке человека, а если определять не по чему —
на русском. Ключи полей, статусы, код, идентификаторы и пути не переводятся; сообщение
коммита — на английском.
