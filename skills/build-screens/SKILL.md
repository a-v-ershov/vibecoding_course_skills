# Build Screens — экраны по потокам на заглушках («UI раньше бэкенда»)

> Файлы `references/…` из этого скилла лежат рядом с этим `SKILL.md` — в папке
> `skills/build-screens/references/` плагина, а не в `skills/_shared/`.

## 📚 Объясни пользователю (перед началом, своими словами, 4–6 предложений)

Этот скилл собирает **рабочие экраны** по карте потоков — но без бэкенда: данные приходят из
**заглушек**, коротких функций, которые отдают заранее заготовленные примеры. Зачем так: экран,
который можно кликать, показывают живым людям за 15 минут, и переделка стоит дёшево — пока к нему
не прикручены API, база и оплата. Если же попросить ИИ «сделать экран», он по привычке сделает
экран, API и таблицу в базе разом, а недостающий бэкенд просто выдумает. Ключевое условие —
**заглушки живут за одной границей**: экран зовёт функцию и не знает, откуда данные; появится
настоящий бэкенд — меняется слой заглушек, экраны остаются как есть. Готовность доказывает не
ИИ словами: на каждый поток пишется UI-тест, который сам ходит по экранам как человек и падает,
если путь не сошёлся; красный тест чинится до зелёного, и только потом поток смотрит человек.
Это не прототип на выброс: экраны настоящие, из компонентов UI-кита и по `DESIGN.md`, и они
останутся в продукте — вместе с тестами.

## Порядок работы (скопируй чеклист в ответ и отмечай по ходу)

```
- [ ] 0. Вход: платформа; потоки, UI-кит, DESIGN.md на месте? → режим: сборка / обновление
- [ ] 1. Учебный блок: UI раньше бэкенда, заглушки за одной границей, тест доказывает готовность
- [ ] 2. Чтение: потоки (экраны, состояния, тексты, стресс-примеры), DESIGN.md, UI-кит, слой 2
- [ ] 3. План: экраны · компоненты UI-кита · контракты заглушек → ПАУЗА, жди одобрения
- [ ] 4. Граница заглушек: контракты + тестовые данные из стресс-примеров + переключатель состояний
- [ ] 5. Сборка экранов потока: все состояния из таблицы, тексты дословно
- [ ] 6. Проверка: автопроверки → UI-тест по потоку → починка до зелёного → человек смотрит сам
- [ ] 7. Обвязка: правила в AGENTS.md проекта — граница заглушек, экраны по потокам
- [ ] 8. Стоп: резюме, живой тест, следующий поток
```

### 0. Вход и режим

**Платформа.** Возьми из `docs/spec/02-tech-architecture.md` и подтверди кодом: признаки — в
`references/platforms.md`, «Шаг 0»; прочитай его на этом шаге. От платформы зависят три вещи
шага 4 (где живут заглушки, чем переключаются состояния, чем проходить поток) — сами шаги
одинаковы для любого стека.

- Нет `docs/spec/04-user-flows.md` → **остановись**: собирать не по чему, карты экранов нет.
  Предложи сначала `/spec-user-flows`. Без неё ИИ выдумает экраны, состояния и тексты сам —
  ровно то, от чего потоки и защищают.
- Нет UI-кита или `DESIGN.md` в корне → предложи сначала `/setup-ui`: без UI-кита ИИ переизобретёт
  кнопки на каждом экране, без DESIGN.md выдаст усреднённый «ИИшный» вид, и всё это придётся
  переделывать. Человек настаивает — скажи, чем рискует, и собирай на том, что есть.
  Натив и Flutter — см. `references/platforms.md`, «Шаг 0».
- Экраны уже собраны → **режим обновления**: спроси, что делаем — следующий поток или пересборка
  конкретного. Экраны других потоков не трогай.
- Аргумент — имя потока. Пусто → предложи главный поток из карты (первый в таблице) и собирай
  **один поток за раз**: так проверка и правки идут маленькими шагами.

### 2. Чтение

- **Потоки (`04-user-flows.md`) — главный источник:** таблица экранов (что на нём, состояния,
  куда ведёт), шаги потока, настоящие тексты, стресс-примеры данных.
- **Шаги `[Система]` и `[Внешний]` — это и есть точки заглушек:** там, где поток уходит в фоновую
  работу или в чужой сервис (оплата, письмо, AI), бэкенда сейчас нет — встаёт заглушка.
- **`DESIGN.md`** (корень проекта) — токены, типографика, Do's and Don'ts.
- **UI-кит** — какие компоненты уже есть и откуда берутся. Где он на платформе —
  `references/platforms.md`, «Шаг 2». Какой именно — решил `/choose-ui-kit`, смотри правила UI
  в AGENTS.md проекта.
- **Слой 2 спеки** — сущности и их поля: контракты заглушек описывай **по схеме данных слоя 2**,
  иначе настоящий бэкенд потом не встанет на место заглушки и экраны придётся править.

### 3. План → ПАУЗА

Покажи компактно, тремя таблицами, и жди одобрения — до него экранов не пишем:

- **Экраны:** экран из потока · где живёт в приложении (маршрут в вебе, экран в навигации —
  в остальных) · состояния из таблицы.
- **Компоненты:** что нужно по колонке «Что на нём» · есть в UI-ките / доставить командой UI-кита.
  Нужного в UI-ките нет → скажи прямо и предложи вариант (соседний компонент UI-кита или сборка
  из примитивов UI-кита), не изобретай молча.
- **Контракты заглушек:** функция · что отдаёт (сущности слоя 2) · какому шагу потока отвечает.

### 4. Граница заглушек — одно место

Каждая точка `[Система]`/`[Внешний]` из потока = одна функция (там, где стек это любит, —
протокол, интерфейс или абстрактный класс с одной stub-реализацией), все они — **в одном
месте**. Где именно и чем переключать состояния — зависит от платформы: таблица, превью и
что делать, если стека в таблице нет, — `references/platforms.md`, «Шаг 4»; прочитай до заглушек.

Правила одинаковы на любом стеке:

- **Экран зовёт функцию и не знает, откуда данные.** Подключение бэкенда — правка одного места.
- **Тестовые данные — из стресс-примеров потоков**, а не «Иван Иванов и три записи»: длинное имя без
  пробелов, 200 строк в таблице, пустой список, текст с эмодзи — то, на чём вёрстка разваливается.
- **Любое состояние из таблицы достижимо без правки кода.** Иначе пустоту и ошибку не увидит
  никто, пока они не случатся у живого человека.
- **Заглушка, которая всегда мгновенно отвечает «успех», бесполезна:** задержку и ошибку она
  тоже должна уметь отдать — иначе состояния «загрузка» и «ошибка» нечем показать.

💡 Поясни пользователю: без этой границы заглушки расползаются по компонентам, и появление
бэкенда превращается в переписывание всего UI.

### 5. Сборка экранов

Поток за потоком, экран за экраном по таблице:

- **Компоненты — из UI-кита**, не рисуем: откуда они на платформе — `references/platforms.md`,
  «Шаг 5».
- **Цвета, шрифты, радиусы — только токены темы из `DESIGN.md`**, не значения: как они выглядят
  на платформе — там же. Хардкод (hex-цвета, произвольные отступы) в разметке не оставляем —
  правила UI в AGENTS.md проекта.
- **Тексты — дословно из потоков:** заголовки, надписи на кнопках, пустые состояния, ошибки.
  Они уже согласованы с человеком — не переписывай и не выдумывай. Текста в потоке нет →
  это вопрос человеку, а не повод сочинить.
- **Все состояния из таблицы** собираются сразу — пусто, загрузка, ошибка, обычное. «Обычное
  сейчас, остальное потом» — это и есть удачный сценарий, от которого потоки защищают.
- **Логику бэкенда не пишем:** ни запросов в БД, ни вызовов внешних API, ни авторизации,
  ни миграций. Понадобилось — это заглушка, а не исключение.

### 6. UI-тест по потоку — написать, прогнать, починить

Сначала автопроверки проекта. Где искать мини-скилл проверок — `references/ui-tests.md`.
Дальше главное: **один поток = один UI-тест**, который ходит по экранам как человек — от точки
входа до финала, включая ветки и состояния из таблицы.

Сценарий не выдумывается: он уже написан в `04-user-flows.md` — там и шаги, и настоящие тексты
кнопок, заголовков, ошибок. Тест сверяет ровно их. Инструмент — по платформе; команду установки
сверь с актуальной официальной инструкцией, не по памяти: таблица и что делать, если стека в ней
нет, — в `references/ui-tests.md`; прочитай его до написания теста.

Что проверяет тест — ровно то, что дают потоки:

- **Путь сходится:** от точки входа до финала; каждая кнопка ведёт туда, куда сказано в потоке.
  Кнопка в никуда — это провал теста, а не мелочь.
- **Все состояния из таблицы** — пусто, загрузка, ошибка, обычное: тест переключает их
  переключателем шага 4 и сверяет настоящий текст из потока.
- **Скриншот на каждом состоянии** — их снимает сам тест: получается и машинная проверка,
  и наблюдаемое доказательство одним прогоном.

**Артефакты прогона — сразу в `.gitignore`**, до первого запуска теста; что туда входит — в
`references/ui-tests.md`.

**Прогони и почини — до зелёного.** Упало → чини **экран**, а не тест: тест написан по потоку,
а поток согласован с человеком. Не сходится — сначала пойми, кто прав: обычно прав поток, а если
неправ он, то правится сначала `docs/spec/04-user-flows.md`, потом код и тест. Подгонять тест
под то, что получилось, нельзя: зелёный тест, проверяющий баг, хуже красного. Починил — прогони
снова; шаг закрыт, когда тест зелёный, а не когда «в основном работает».

**Тест зелёный — теперь человек.** Зелёный тест не значит «хорошо»: он проверяет, что элемент
на месте, и не видит, что вёрстка поехала, текст обрезался, кнопка ушла за край или экран
непонятен. Поэтому, когда тест зелёный, покажи скриншоты состояний и **попроси человека пройти
поток самому** — дай ему всё, чтобы не искать: где открыть (адрес экрана или команда запуска),
как переключать состояния, что по потоку должно получиться. Его правки — обычная работа шага,
а не «замечания на будущее»: вернулся с ними → почини и прогони тест снова.

💡 Поясни пользователю, почему этот UI-тест надёжен, — `references/ui-tests.md`.

### 7. Обвязка — правила в AGENTS.md проекта

Допиши в раздел правил разработки (если таких строк ещё нет; путь заглушек подставь свой —
из таблицы шага 4): строки — в `references/templates.md`, «Шаг 7».

💡 Поясни: без правила ИИ в следующей сессии сходит в базу прямо из компонента, и граница,
ради которой всё делалось, исчезнет.

### 8. Стоп (жёсткая пауза)

Покажи резюме: собранные экраны и где они живут, число состояний со скриншотами, UI-тест
и его результат, что стоит на заглушках, открытые вопросы. Скажи: текст — в
`references/templates.md`, «Шаг 8».

Никогда не начинай бэкенд и не подключай настоящие API в этой сессии без явной просьбы человека.

## Правила сжатия вывода

- План шага 3 — таблицами, не прозой; по одной строке на экран, компонент и контракт.
- Один поток за раз: собрал → проверил → показал. Не собирай все потоки разом.
- Код экрана не пересказывай в чате — показывай скриншот и где экран живёт.

## Правила

- Стек не предполагаем: платформу берём из слоя 2 и кода (шаг 0). Веб-умолчания (`lib/stubs/`,
  query-параметр, браузер) — не универсальны; у остальных платформ своё, таблица шага 4.
  Стека нет и в таблице — выводим три вещи по обычаю стека и говорим об этом человеку.
- Бэкенд не пишем: заглушки — единственный источник данных, пока человек не попросит иначе.
- Тексты, состояния и переходы берём из потоков; чего в потоках нет — вопрос человеку.
  Меняется экран → сначала правь `docs/spec/04-user-flows.md`, потом код.
- Экран без всех состояний из таблицы — не готов; «потом добавим» не считается.
- Поток не закрыт, пока UI-тест по нему не зелёный. Тест упал → чинится экран; подгонять тест
  под получившееся нельзя. Зелёный тест — не финал: дальше поток смотрит человек.
- Компоненты — только из UI-кита: установленного (веб, Expo), системного (натив) или встроенного
  во фреймворк (Flutter, Compose Multiplatform). Вид — только токенами темы из `DESIGN.md`.
- Контракты заглушек — по сущностям слоя 2, чтобы бэкенд встал на их место без правки экранов.
- Артефакты прогона (скриншоты, отчёты, трейсы, видео, кэш раннера) и любые временные файлы —
  в `.gitignore` сразу, до первого запуска: их пересоздаёт прогон, а в репозитории они пухнут
  и захламляют дифф.
- Команды UI-кита сверяй с актуальной официальной инструкцией, не по памяти.
- Факты (платформа, UI-кит, токены, стек) ищи сам в коде и документах; у человека спрашивай только
  решения — с рекомендованным вариантом первым.
- Пиши просто: что шаг делает и зачем. Без художественных оборотов и отсылок
  («та самая беда», «как у всех», «лечим»).
- **Финальный отчёт — по общему формату** (`skills/_shared/report-format.md` этого плагина):
  первой строкой итог, детали — в документ, в конце — блок «Что делать дальше».

умолчанию русский. Код, идентификаторы, пути и имена токенов не переводятся.
