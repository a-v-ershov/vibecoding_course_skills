# Справочник: как дотянуться до данных

**Собрано: январь 2026** (по знанию модели на момент написания скилла). Команды CLI и названия
разделов у платформ меняются — это подсказка, где искать, а **не** список команд для слепого
выполнения. Всегда сначала смотри, что за площадка и база у **этого** проекта (конфиг деплоя,
переменные окружения, спека), и сверяй команду со справкой самого инструмента (`--help`).

Правило поверх всего справочника: **в боевой среде — только чтение**.

## 1. База данных

Главный источник для «сколько людей» и «сколько действий»: почти всё уже лежит в обычных
таблицах продукта.

| Как подключиться | Когда подходит |
|---|---|
| Строка подключения из переменной окружения боевой среды | универсальный путь; переменную ищи в конфиге деплоя, значение не печатай |
| CLI платформы базы (`psql`, `supabase`, `mysql`, консоль облака) | когда прямой доступ закрыт, а CLI авторизован |
| Внутренний эндпоинт самого приложения (если продукт его отдаёт) | когда до базы снаружи не дотянуться |
| Веб-консоль SQL в кабинете провайдера | последний вариант: результат придётся принести человеку руками |

Гигиена запросов к бою: только `SELECT`, всегда с фильтром по периоду, выборки строк с `LIMIT`,
никаких блокирующих операций. Если у провайдера есть пользователь только для чтения — лучше он.

### Заготовки запросов (переписать под схему проекта)

Имена таблиц и полей ниже — плейсхолдеры. Настоящие бери из миграций проекта.

```sql
-- новых пользователей за период и за предыдущий такой же
select count(*) filter (where created_at >= :from and created_at < :to)   as current,
       count(*) filter (where created_at >= :prev_from and created_at < :from) as previous
from users;

-- активные: сколько разных людей сделали хоть одно ключевое действие
select count(distinct user_id) from <таблица_действий>
where created_at >= :from and created_at < :to;

-- ключевое действие в разрезе статуса (успех / ошибка)
select status, count(*) from <таблица_действий>
where created_at >= :from and created_at < :to group by status;

-- воронка: сколько людей дошло до каждого шага
select
  count(distinct u.id)                                        as registered,
  count(distinct a.user_id)                                   as started,
  count(distinct a.user_id) filter (where a.status = 'done')  as finished,
  count(distinct p.user_id) filter (where p.status = 'succeeded') as paid
from users u
left join <таблица_действий> a on a.user_id = u.id and a.created_at >= :from
left join payments p           on p.user_id = u.id and p.created_at >= :from
where u.created_at < :to;

-- фоновые задачи: упавшие за период (имя таблицы зависит от очереди)
select name, count(*) from <таблица_очереди>
where state in ('failed','dead') and created_on >= :from group by name;
```

Часовой пояс: если поля хранятся в UTC, а отчёт человек читает в своём поясе — приводи границы
явно и напиши в шапке отчёта, в каком поясе они посчитаны.

## 2. Логи приложения

| Где живут | Как достать | Особенность |
|---|---|---|
| Логи платформы деплоя (PaaS, облако) | CLI платформы или её кабинет | хранятся недолго — часы или дни; за месяц по ним не сравнить |
| Контейнер на своём сервере | `docker logs --since <период> <контейнер>` | ограничивай период, иначе выгрузишь гигабайты |
| Файл на сервере | `journalctl --since`, чтение файла с фильтром | смотри ротацию: старое могло уехать в архив |
| Сервис хранения логов | API или веб-интерфейс | самый удобный поиск, если подключён |
| Сборщик ошибок (Hawk в РФ, Sentry — международный, GlitchTip) | API проекта | ошибки уже сгруппированы — бери оттуда, а не из сырых логов |
| Локальная среда | вывод команды запуска проекта, файл лога локального стека | это тестовые данные, помечай отдельно |

Как считать ошибки, если логи неструктурированные: фильтр по уровню (`error`, `ERR`, `Exception`,
`Traceback`), затем группировка по устойчивой части сообщения (без идентификаторов и дат) —
и в отчёт идёт «тип × количество × пример», а не сырая простыня. Если уровня в логах нет вообще —
это находка для `/plan-analytics`, а не повод считать, что ошибок не было.

## 3. Внешние сервисы

- **Сервис продуктовой аналитики** — если подключён, у него есть API для выгрузки цифр за
  период; ключ бери из окружения, значение не печатай. Типовые: Яндекс.Метрика (Logs API /
  API отчётов) и AppMetrica для мобилок в РФ, GA4 (Data API) и PostHog (query API) —
  международные. Какой именно в проекте — смотри в `docs/analytics.md`.
- **Платёжный провайдер** — сумма и количество платежей надёжнее считаются по своей таблице
  платежей; кабинет провайдера нужен, когда расходятся статусы.
- **Платные API (LLM и подобные)** — расход обычно виден в кабинете провайдера; если в проекте
  пишется своя таблица использования, считай по ней и скажи, что это оценка.

## 4. Живой ли сервис

Для боевой среды — короткая проверка доступности: запрос к health-эндпоинту, если он есть,
иначе к главной странице; смотрим код ответа и время. Это одна строка в блоке «здоровье»
и одновременно проверка, что отчёт вообще смотрит на работающий продукт.

## 5. Если дотянуться не удалось

Не подставляй локальные данные вместо боевых и не пиши ноль. В отчёт идёт строка:
что за источник · почему недоступен · что нужно человеку сделать, чтобы в следующий раз
он посчитался (задать переменную, авторизовать CLI, открыть доступ к базе).
