# Инициализация проекта — от спеки к живому рабочему месту

## 📚 Объясни пользователю (перед началом, своими словами, 5–7 предложений)

Спека — план на бумаге; инициализация превращает её в живой проект: папка с каркасом кода,
локальное окружение, git-история и инструкции. Это рабочее место сразу для двоих: человек
получает проект, который поднимается одной командой (сайт на localhost, приложение в
симуляторе), ИИ — окружение для петли проверки из слоя 3. Три принципа. Первый: сначала
смотрим, что уже есть, — скилл можно перезапускать, он пропускает готовое и ничего не
затирает. Второй: внутри папки проекта ИИ действует сам, а всё глобальное на компьютере —
установки программ, аккаунты, ключи — только с явного разрешения или руками человека.
Третий: «готово» — это не «файлы созданы», а «поднялось одной командой, и мы это увидели
своими глазами» — проверка запуска. Функциональность продукта здесь не строится — фичи
пойдут по плану разработки следующим этапом.

## Порядок работы (скопируй чеклист в ответ и отмечай по ходу)

```
- [ ] 0. Вход: прочитай docs/spec/ (спеки нет → интервью через gather-context)
- [ ] 1. Учебный блок: что такое инициализация и зачем
- [ ] 2. Разведка (только чтение): ОС, инструменты, что уже есть в папке
- [ ] 3. План трёх списков — отдельным сообщением, по-человечески; жди одобрения
- [ ] 4. Инструменты: доставь недостающее или объясни человеку, что и как поставить
- [ ] 5. Git: init + .gitignore под стек + .env.example; работа в ветке main; GitHub (gh)
- [ ] 6. Каркас: приложение + локальное окружение слоя 3 + seed + мини-скиллы
- [ ] 7. Проверка запуска: подними одной командой и докажи наблюдаемым результатом
- [ ] 8. Документация: docs/dev/setup.md + CLAUDE.md проекта (по шаблонам) + память Claude
- [ ] 9. Первый коммит в main (сообщение на английском) + push, если создавали GitHub
```

### 0. Вход — спека

Прочитай все три слоя `docs/spec/`: слой 2 даёт стек, компоненты и секреты; слой 3 — запуск
одной командой, seed, локальные заменители и мини-скиллы; слой 1 — контекст (что вообще
строим). Стек берётся из слоя 2, каким бы он ни был: веб на Node.js, нативное iOS-приложение
на Swift, бот на Python — шаги скилла одни и те же, меняются только инструменты. Рабочие
мелочи, на которые спека не отвечает (имя пакета, порт, версия), — спроси по ходу одной
строкой, не изобретай молча.

Спеки нет совсем → скажи, что правильный путь — сначала `/create-spec`, и предложи его.
Человек хочет инициализацию сразу → вызови скилл `gather-context` (через Skill tool)
с минимумом тем: стек и платформа (веб / мобильное / другое; фронтенд, бэкенд, база — что
из этого есть), внешние сервисы и их ключи, как запускать локально, что при проверках
заменяем заглушками. Дальше работай по собранному контексту как по спеке.

### 2. Разведка — только чтение

Ничего не меняя, выясни:

- **ОС и архитектура** (macOS / Linux / Windows, arm/x86) — от этого зависят команды
  установки и сама возможность стека (нативная iOS-разработка требует macOS с Xcode);
- **инструменты стека на месте?** Список выведи из слоёв 2–3, не из привычки: git — всегда;
  дальше по стеку — Node.js и Docker для веба, Xcode и его командные инструменты для iOS,
  Python для бота, и так далее. У каждого проверь и версию, и состояние (Docker может
  стоять, но демон не запущен — `docker info`); gh — есть ли и авторизован ли (`gh auth status`);
- **что уже есть в папке:** git-репозиторий? каркас кода (`package.json`, `*.xcodeproj`,
  `pyproject.toml`…)? `.gitignore`, `CLAUDE.md`, `.env.example`, `docs/`?

Всё найденное — в копилку «уже есть»: дальше такие шаги пропускаются, существующие файлы
дополняются, а не переписываются.

### 3. План — три списка (жди одобрения)

Покажи план **отдельным сообщением, которым ход заканчивается**, — никаких вызовов
инструментов после него. Не выводи план перед вызовом инструмента и не прячь его внутрь
вопроса AskUserQuestion: в некоторых интерфейсах (например, расширение VSCode) текст перед
вызовом инструмента не показывается — человек увидит вопрос «одобряешь план?» без самого
плана.

Каждый пункт плана — действие или команда **плюс одна строка обычным, нетехническим
языком: что это и зачем в этом проекте**. Например: `supabase start` — «поднимает на
твоём компьютере локальную копию базы данных, чтобы проект работал без облака и бесплатно»;
`.gitignore` — «список файлов, которые git не сохраняет: мусор, сборка, секреты». Три
списка, каждая строка следует из спеки:

1. **«Сделаю сам»** — файлы внутри папки проекта: каркас, `.gitignore`, seed, доки.
   Безопасно, откатывается git-ом.
2. **«Поставлю сам, но спрошу»** — глобальные установки на компьютер; у каждой — точная
   команда под ОС из разведки (brew / apt / winget…).
3. **«Только ты»** — что ИИ сделать не может: скачать Docker Desktop, поставить Xcode из
   App Store, создать аккаунт, получить API-ключ. По каждому: что это, зачем в проекте,
   где взять (ссылка). Для ключей платных API — сразу напомни поставить у провайдера
   лимит трат: утёкший ключ — это чужие расходы на твоей карте.

Одобрение — следующий ответ человека обычным сообщением («да», «поехали», «да, но без
push»…). Попросил поправить → поправь план, покажи заново тем же способом и снова жди.
Если критичный пункт из списка 3 блокирует запуск — честно скажи: инициализация дойдёт
до этого места и встанет на паузу, продолжим после установки.

### 4. Инструменты

- Ставь по одному пункту списка 2, каждый — только после «да»; после установки проверь,
  что инструмент реально появился (`command -v`, версия).
- Инструмент стоит, но не работает (демон Docker не запущен, Xcode без лицензии или без
  симуляторов) → попроси человека запустить/донастроить (или предложи команду) и дождись
  подтверждения.
- Поставить сам не можешь (установка с сайта или из App Store, нет прав, нет менеджера
  пакетов) → одна короткая инструкция человеку: что скачать, откуда, что нажать — и жди,
  пока поставит. Не притворяйся, что уже поставлено, и не продолжай, если без этого
  дальнейшие шаги упадут.
- То же — с любым компонентом, который не настраивается из командной строки: веб-консоль
  сервиса, графический установщик, параметры в облаке. Дай короткую пошаговую инструкцию —
  что открыть, куда нажать, что ввести и что вернуть тебе (например, какой ключ положить
  в `.env`) — и продолжай только после результата.

### 5. Git и GitHub

- Папка ещё не git-репозиторий → `git init`. `.git` уже есть → не трогай и заново
  не инициализируй.
- **Одна ветка — `main`.** Убедись, что текущая ветка называется `main` (`git branch -M main`
  сразу после `git init`, если генератор назвал её иначе), и дальше работай только в ней:
  ни ИИ, ни скилл не создают отдельных веток — ни «под фичу», ни «чтобы не сломать», —
  пока человек не попросит об этом явно. Объясни человеку одной строкой: ветка — это
  параллельная копия проекта, её потом надо сливать обратно, а в маленьком проекте с одним
  разработчиком это лишние шаги; проще вести всё линейно в `main`. Это правило переживёт
  инициализацию: в шаге 8 оно попадёт в `CLAUDE.md` проекта и в память Claude.
- **`.gitignore` под стек:** возьми общепринятый шаблон для стека из слоя 2 (генератор
  каркаса часто создаёт свой — тогда дополни его). Для веба — зависимости и сборка
  (`node_modules`, `.next`, `dist`); для iOS — `DerivedData`, `xcuserdata`, `Pods`; плюс
  мусор ОС (`.DS_Store`, `Thumbs.db`), артефакты инструментов слоя 3 (временные файлы
  локальной базы) и `.env` со всеми вариантами. Существующий `.gitignore` дополняй
  недостающими строками, не переписывай.
- **`.env.example`:** все ключи из раздела «Секреты» слоя 2 с заглушками-значениями и
  комментарием «где взять». Настоящий `.env` — только локально, в `.gitignore`, никогда
  в коммитах. Секретам нельзя давать «публичные» префиксы (`NEXT_PUBLIC_`, `VITE_` и
  подобные у других инструментов): такие переменные вшиваются в код, который получает
  каждый посетитель сайта. В стеках без файла `.env` (нативное приложение) — тот же
  принцип в форме, принятой у стека (конфигурация вне репозитория).
- **GitHub:** сначала посмотри `git remote -v` — origin уже настроен → удалённый
  репозиторий есть, вопрос не задавай (в шаге 9 просто пушь в него). Иначе **спроси одним
  вопросом** (AskUserQuestion): создавать ли репозиторий на GitHub, и если да — публичный
  или приватный. Нужен → работай через GitHub CLI (`gh`): его нет — это глобальная
  установка по правилам шага 4 (поставить + `gh auth login`, вход делает человек); есть →
  `gh repo create <имя> --private|--public --source=. --remote=origin`.
  Не нужен → пропусти: локального git достаточно, GitHub можно добавить позже.
  Репозиторий создан → одна строка про защиту от утечек: у публичных GitHub сам блокирует
  отправку ключей известных форматов (push protection включена по умолчанию), у приватных
  на бесплатном тарифе такой защиты нет — надеяться на неё нельзя, чистоту коммитов
  проверяем сами (шаг 9).

### 6. Каркас

- **Кода нет** → создай каркас штатным генератором стека из слоя 2: для веба —
  `create-next-app` и подобные, для iOS — шаблон проекта Xcode, для Python — стандартная
  структура пакета. Генератор даёт общепринятую структуру — руками каркас не выдумывай.
  **Код есть** → ничего не пересоздавай, только донастрой недостающее.
- **В текущую папку и без вложенного `.git`.** Генератор не должен создавать собственный
  git-репозиторий: `git init` уже сделан шагом 5 (большинство генераторов видят внешний
  репозиторий и не создают свой), а если у генератора есть явный флаг — используй его
  (у `create-next-app` это `--disable-git`). Генератор отказывается работать в непустой
  папке (в проекте уже лежат `.claude/`, `CLAUDE.md`, `docs/`) → сгенерируй во временную
  подпапку, перенеси её содержимое в корень проекта, подпапку удали. Перед первым коммитом
  убедись, что вложенного `.git` не появилось; появился → удали его (истории в нём нет,
  только автоматический коммит генератора).
- **Локальное окружение слоя 3:** локальные заменители облачных компонентов (например,
  локальная база в docker), seed-скрипт с тестовыми данными ровно из слоя 3,
  переключатель моков (включён по умолчанию) и место под заготовленные тестовые ответы.
  Сами моки внешних API наполняются на этапе разработки — вместе с кодом, который их зовёт.
- **Запуск одной командой** из слоя 3 — собери эту обёртку; она и есть главный вход в
  проект для человека и для ИИ. Для веба — например, `npm run dev:all` (база + сервер +
  seed); для iOS — сборка и запуск в симуляторе одной командой.
- **Гигиена пакетов.** Ставь только настоящие и популярные пакеты: имя без опечаток,
  пакет существует давно и активно скачивается. ИИ иногда выдумывает правдоподобные имена
  пакетов, а злоумышленники регистрируют их заранее и кладут внутрь вредоносный код —
  сомневаешься → проверь пакет в реестре (npm, PyPI…) до установки.
- **Мини-скиллы слоя 3** → `.claude/skills/<имя>/SKILL.md` по шаблону из
  `references/templates.md`. Полноценно рабочими делай те, чья команда уже существует
  (сброс окружения, прогон проверок); тем, кому нужен ещё не написанный код продукта
  (например, прогон полного сценария), — рабочий каркас с пометкой TODO: доделывается
  на этапе разработки.
- **По желанию — «охранник» за плечом ИИ:** официальный плагин `security-guidance`
  (https://claude.com/plugins/security-guidance). Объясни человеку простыми словами:
  пока ИИ пишет код, плагин в фоне просматривает каждую правку на типовые дыры
  безопасности — секрет, попавший в код, инъекции, небезопасную работу с данными — и
  предупреждает сразу, а не когда проект уже опубликован. Человек согласен → пусть
  выполнит `/plugin install security-guidance@claude-plugins-official` и при установке
  выберет область **«project»** — плагин включится только для этого проекта, не трогая
  остальные.

### 7. Проверка запуска

Подними окружение той самой одной командой и докажи наблюдаемым результатом. Что именно
проверять — зависит от стека, по слою 3:

- **приложение живо:** сайт — страница отвечает (скриншот через браузер, если доступен,
  иначе ответ сервера 200 с телом); нативное приложение — сборка прошла и приложение
  открылось в симуляторе (скриншот симулятора);
- **база жива и seed лёг** (если база есть в стеке) — покажи строку тестового пользователя
  запросом к базе;
- **мини-скиллы работают** — прогони сброс окружения и прогон проверок.

«Ошибок в логах нет» — не доказательство. Красное → чини и повторяй; окружение не готово,
пока проверка не зелёная. Починить не выходит — честно покажи ошибку и предложи варианты,
не объявляй готовым.

### 8. Документация

- **`docs/dev/setup.md`** на русском по шаблону №1 из `references/templates.md`: что должно
  стоять на компьютере, как поднять, адреса и тестовые пользователи, сброс, мини-скиллы,
  реальные ключи, частые проблемы. Пиши по фактам своей же проверки запуска, не по планам.
- **`CLAUDE.md` проекта** по шаблону №2: коротко — суть, стек, команды, правила — включая
  **правило одной ветки** (`main`, отдельные ветки — только по явной просьбе человека) и
  **правила безопасности**: они фиксируются сейчас, чтобы этап разработки строил по ним
  с первого дня, а не «прикручивал потом» (безопасность сама не случается).
  Существующий `CLAUDE.md` дополняй, не затирай.
- **Память Claude.** `CLAUDE.md` читается в этом проекте; память — то, что ИИ помнит о работе
  с человеком между сессиями. Продублируй туда правило одной ветки: если механизм постоянной
  памяти доступен, сохрани отдельной заметкой (тип `project`) факт «в этом проекте git
  работает только в ветке `main`; новых веток не создавать, пока человек не попросит явно»
  с пояснением зачем — и добавь строку-указатель в индекс памяти (`MEMORY.md`). Скажи
  человеку одной строкой, что записал: это перекрывает общую привычку инструментов
  «сначала создай ветку, потом коммить».

### 9. Первый коммит и итог

- Перед `git add` посмотри `git status`: `.env` и мусор не должны попасть в коммит.
  Плюс быстрый поиск секретов по добавляемым файлам (ключеподобные строки: `sk-`, `AKIA`,
  длинные случайные токены) — история git помнит всё, и первый коммит — единственный шанс
  начать её чистой.
- Ключ всё же попал в коммит или засветился где-то ещё → его **перевыпускают** у провайдера,
  а не просто стирают из кода: боты сканируют публичные репозитории за минуты, а старые
  версии файлов остаются в истории git.
- Первый коммит — **в `main`**, с сообщением на английском (например,
  `Initialize project: app skeleton, local env, docs`). Отдельную ветку под него не заводи,
  даже если общее правило инструмента советует «сначала ветку»; создавали GitHub →
  `git push -u origin main`.
- Итог-резюме тремя списками: **сделано** · **пропущено (уже было)** · **осталось человеку**
  (какие ключи и аккаунты, где взять). Следующий шаг курса — план разработки (`docs/tasks/`).

## Правила

- Скилл не привязан к стеку: веб, нативное мобильное приложение, бот — шаги те же,
  инструменты и проверки выводятся из слоёв 2–3.
- Глобальные установки, ключи и аккаунты — только с явного «да» или руками человека;
  внутри папки проекта действуй сам.
- Перезапуск безопасен: готовое пропускай, существующие файлы дополняй, ничего не затирай.
- Каждый шаг следует из спеки; спека молчит → спроси, ничего «на всякий случай».
- Работа идёт в одной ветке `main`; отдельные ветки — только по явной просьбе человека.
  Правило закрепляется в `CLAUDE.md` проекта и в памяти Claude (шаг 8), чтобы действовать
  и после инициализации.
- «Готово» = проверка запуска зелёная; «файлы созданы» и «ошибок нет» — не готовность.
- Функциональность продукта не строим — только каркас и окружение; фичи — этап разработки.
- Секреты — только в `.env` (он в `.gitignore`) или локальной конфигурации стека,
  никогда в коде и коммитах; без «публичных» префиксов; утёкший ключ перевыпускается,
  а не стирается.
- Безопасность закладывается при инициализации, а не «потом»: чистая git-история,
  настоящие пакеты, правила безопасности в `CLAUDE.md` проекта.
- Объясняй незнакомое одной строкой простыми словами (`.gitignore`, seed, проверка
  запуска, переменные окружения) — аудитория часто не программисты.
- План (шаг 3) и итог (шаг 9) — отдельным текстовым сообщением, которым ход заканчивается:
  текст перед вызовом инструмента виден не во всех интерфейсах, человек должен прочитать
  план, прежде чем что-то одобрять.
