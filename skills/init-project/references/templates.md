# Шаблоны init-project

Три шаблона: инструкция по окружению, CLAUDE.md проекта, мини-скилл. Всюду: разделы без
содержания не пишутся; таблицы вместо прозы; подставляй факты своей проверки запуска,
не планы. Примеры в шаблонах — для веб-стека; для другого стека (нативное приложение, бот)
подставляй его инструменты и способ запуска, структура разделов та же.

## 1. docs/dev/setup.md — инструкция по окружению (на русском)

```markdown
# Локальное окружение — <Название проекта>

> Как поднять проект и как им пользоваться · Дата: <YYYY-MM-DD>
> Основа: docs/spec/02-tech-architecture.md, docs/spec/03-dev-architecture.md

## Что должно стоять на компьютере

| Инструмент | Зачем | Проверка |
|-----------|-------|----------|
| <инструмент стека: Node.js / Xcode / Python… ≥ версия> | <зачем> | <команда: `node -v`…> |
| Docker (запущенный) — если есть в стеке | <зачем> | `docker info` |

## Поднять одной командой

- `<команда>` — что поднимает, по пунктам.
- Остановить всё разом: `<команда остановки>` (есть только если поднимаются фоновые
  сервисы — сервер, база, воркер; данные сохраняются, это не сброс).
- Открыть: `http://localhost:<порт>` (или: приложение открывается в симуляторе),
  войти тестовым пользователем `<email>` / `<пароль>`.
- <Другие адреса: ловец писем, консоль базы…>

## Тестовые данные

- Кто есть в seed и зачем каждый (одна строка на пользователя/запись).
- Сброс в чистое состояние: `<команда>` (или мини-скилл `/<имя скилла сброса>`).

## Мини-скиллы

| Скилл | Что делает | Статус |
|-------|-----------|--------|
| `/<имя>` | <что> | готов |
| `/<имя>` | <что> | каркас — доделывается на этапе разработки |

## Реальные ключи (для ручной проверки без моков)

Локальные проверки идут на заглушках (`<флаг>` включён по умолчанию) — ключи не нужны.
Для реального режима:

| Ключ | Где взять | Куда положить |
|------|-----------|---------------|
| <KEY> | <сервис, ссылка> | `.env` (по образцу `.env.example`) |

- Получая ключ платного API, сразу поставь у провайдера **лимит трат** (стоп-кран):
  утёкший ключ — это чужие расходы на твоей карте.
- Ключ засветился (в коммите, чате, на экране) → **перевыпусти** его у провайдера;
  просто удалить из кода недостаточно.

## Частые проблемы

- <симптом> → <что сделать>
```

## 2. CLAUDE.md проекта (короткий; существующий — дополнять, не затирать)

```markdown
# <Название проекта>

<Одна строка: что за продукт.>
Спецификация: `docs/spec/` (3 слоя) · Окружение: `docs/dev/setup.md`.

## Стек

<Одна-две строки: главное из слоя 2.>

## Команды

| Команда | Что делает |
|---------|-----------|
| `<dev:all>` | поднять всё локально |
| `<stop>` | остановить всё локально (только если есть фоновые сервисы; данные не теряются) |
| `<reset>` | сброс окружения + seed |
| `<checks>` | линт и тесты |

## Бюджет и инструменты

- Потолок: `<N ₽/мес>`. Оплата: `<чем>`. Разовые траты: `<допустимы ли>`.
- Зафиксировано: `<хостинг — X · модель ИИ — Y>`. Альтернативы к этому не предлагаются.
- Новый платный сервис, платный тариф или платный пакет не подключается без явного «да»
  человека: сначала предлагается бесплатный или уже стоящий в проекте вариант.
- У каждого платного ключа — лимит трат на стороне провайдера.

<!-- Переносится из раздела «Бюджет и ограничения по инструментам» слоя 2 спеки. -->

## Правила

- Результат доказывается наблюдаемо (скриншот, строка в БД, ответ сервера) — см. слой 3.
- Красный тест — сработавшая сигнализация, а не поломка: чинится **код**, а не тест.
  Добиваться зелёного правкой самого теста (ослабить проверку, `if` под конкретный вход,
  подогнать данные) нельзя — смотри дифф теста. ИИ не проверяет сам себя: «главное, чтобы
  позеленело» — не цель; цель — наблюдаемо верное поведение продукта.
- Моки внешних API включены по умолчанию (`<флаг>`).
- Git ведётся в одной ветке — `main`: коммиты идут прямо в неё, новые ветки не создаются
  (даже «под фичу» или «чтобы не сломать»), пока человек не попросит об этом явно.
- Сообщения git-коммитов — на английском.

## Стиль кода

<!-- База — канон выбранного стека: как принято у фреймворка, так и пишем. Сюда записываются
     только настоящие развилки (у стека 2–3 равноправных варианта) и то, чего не проверит
     линтер; всё, что умеет проверять форматтер/линтер, живёт в их конфигах, а не здесь.
     Держи раздел коротким: ИИ читает его в каждой сессии. -->

- Организация кода: `<по фичам / по слоям — что выбрали и одна строка почему>`.
- Имена — канон стека; словарь домена — из спеки (слой 1), свои синонимы не изобретаются.
- Комментарии объясняют «почему», а не пересказывают код; докстринги: `<где обязательны>`.
- Ошибки: `<единый способ — что видит человек, что уходит в лог>`.
- Тесты — в стиле соседних тестов, на самом дешёвом уровне, доказывающем поведение.

## Правила безопасности

- Секреты — только в `.env` (не коммитится) и только на сервере; никаких «публичных»
  префиксов (`NEXT_PUBLIC_`, `VITE_`…) у секретов.
- База с прямым доступом клиента (например, Supabase) → защита на уровне строк (RLS)
  включается вместе с каждой новой таблицей, не «потом».
- Эндпоинт, дергающий платный API, получает ограничение частоты запросов (rate limiting)
  сразу при создании.
- Новые пакеты — только настоящие и популярные: имя без опечаток, проверка в реестре.
- Перед публикацией — `/security-review` или промпт «проверь проект на дыры»;
  утёкший ключ — перевыпустить, а не стереть.
```

## 3. Мини-скилл — .claude/skills/<имя>/SKILL.md

```markdown
---
name: <имя>
description: "<Что делает и когда запускать, одной-двумя строками. Например: сбросить
локальное окружение в чистое состояние (миграции + seed) перед проверкой с чистого листа.>"
---

Выполни `<команда>`. Дождись конца и покажи одну строку итога — наблюдаемый результат
(что пересоздано / сколько проверок зелёные). Ошибка → покажи её текст и предложи починку.
```
