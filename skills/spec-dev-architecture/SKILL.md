# Слой 3 — Девелоперская архитектура («КАК запускать и как ИИ проверяет себя»)

## 📚 Объясни пользователю (перед началом, своими словами, 5–7 предложений)

Третий слой — самый непривычный и самый ценный. ИИ-агент по умолчанию норовит сказать «готово»,
как только код скомпилировался, — но «скомпилировалось» не значит «работает». Слой 3 даёт ИИ
«глаза и руки»: окружение, в котором он может **сам запустить продукт, прогнать пользовательский
сценарий, УВИДЕТЬ настоящий результат** (не «код написан», а «карточка реально появилась в базе и
на экране»), прочитать ошибку и починить — без человека в цикле. Ключевое правило: «ошибок нет» —
это НЕ доказательство; доказательство — скриншот экрана, строка в базе, конкретный ответ сервера.
Чем шире и быстрее эта петля, тем выше качество, которого ИИ достигает сам. Здесь мы только
**планируем** (что записать в спеку про окружение и проверки) — реальная настройка будет на этапе
разработки. На выходе — компактный файл `docs/spec/03-dev-architecture.md`.

## Порядок работы (скопируй чеклист в ответ и отмечай по ходу)

```
- [ ] 0. Прочитай docs/spec/01-*.md и 02-*.md (нет файлов → см. ниже)
- [ ] 1. Учебный блок: объясни, что такое слой 3 и зачем
- [ ] 2. (существующий проект) Посмотри, что уже есть: команды запуска, тесты, seed
- [ ] 3. Интервью: вызови скилл gather-context с темами слоя 3
- [ ] 4. Проверка в интернете: подтверди инструменты петли проверки
- [ ] 5. Черновик по references/template.md → docs/spec/03-dev-architecture.md
- [ ] 6. Критика: агент spec-critic проверяет черновик, возвращает пробелы
- [ ] 7. Доработка: 🔴 — с человеком, 🟡 — по своему суждению
- [ ] 8. Финал: спека из трёх слоёв готова — итоговое резюме
```

### 0. Вход — слои 1 и 2

Из слоя 1 берутся сценарии для петли проверки (каждая фича с критерием «дано — когда — тогда» —
это готовый сценарий); из слоя 2 — компоненты, которым нужны локальные заменители. Если файлов нет —
предложи начать с `/spec-requirements` (или `/create-spec`); без них слой 3 будет абстрактным.

### 2. Существующий проект

Посмотри, что уже есть: команды запуска (`package.json` scripts, Makefile, docker-compose),
тесты, seed-скрипты, CI. Это «как есть» — в интервью подтверждай и спрашивай только про
недостающее.

### 3. Интервью — темы слоя 3

Вызови скилл `gather-context` (через Skill tool) с темами ниже. Большинство ответов здесь можешь
рекомендовать сам из слоя 2 (стек диктует инструменты) — человек в основном подтверждает.

**Объясняй непривычные понятия простыми словами.** Слой 3 полон вещей, незнакомых непрограммисту, —
seed, петля проверки, MCP, локальные заменители. Прежде чем спросить, объясни одной строкой, что
это и зачем в этом продукте (например: «seed — заранее заготовленные тестовые данные, чтобы было
на чём проверять, не вводя всё руками каждый раз»; «MCP — способ дать ИИ прямой доступ к базе или
логам, чтобы он сам смотрел, что данные легли»). Про каждый рекомендованный инструмент — строка,
что он делает и зачем он в петле проверки. Человек отвечает «не знаю» / «а что это?» — объясни
проще или подробнее, не продавливай.

1. **Запуск одной командой.** Что должно подняться локально одной командой, чтобы продукт был
   готов к работе целиком — и для ИИ, и для человека (какой адрес открыть, каким тестовым
   пользователем войти).
2. **Тестовые данные (seed) и сброс.** Какой набор тестовых данных нужен, чтобы было на чём
   проверять (тестовый пользователь, пара записей), и как быстро сбросить окружение в чистое
   известное состояние.
3. **Петля проверки — ядро слоя.** Для каждого ключевого сценария из слоя 1: как ИИ его
   **прогонит** (шаги) и чем **докажет** настоящий результат — скриншот конкретного экрана,
   строка в базе, ответ сервера. «Тесты зелёные» без наблюдаемого результата — не доказательство.
4. **Инструменты для ИИ.** Браузерная автоматизация (реально открывать экраны, кликать, делать
   скриншоты — например, Playwright MCP); MCP-подключения (доступ к базе, логам);
   собственные мини-скиллы-обёртки — короткие команды вроде «прогони тесты» / «сбрось
   окружение», чтобы типовая проверка вызывалась по имени.
5. **Локальные заменители.** Какие облачные компоненты из слоя 2 при автоматических проверках
   заменяем локальными аналогами или фиксированными ответами (база, хранилище, почта, ИИ-модель) —
   чтобы проверки были быстрыми, бесплатными и не трогали реальные данные. Здесь фиксируем саму
   идею; конкретные контейнеры/образы — забота этапа разработки.

### 4. Проверка в интернете — подтверди инструменты

Перед черновиком сделай пару точечных поисков в интернете (обычно 2–3, это не глубокое
исследование): чем сейчас реально пользуются для петли проверки под стек из слоя 2 —
браузерная автоматизация, MCP-серверы (база данных, логи), локальные заменители облачных
сервисов. Учитывай рынок из слоя 1, если он влияет на выбор. Если проверка изменила
рекомендацию из интервью — покажи старый и новый вариант одной строкой и получи
подтверждение человека.

### 5–7. Черновик → критик → доработка

Напиши черновик по `references/template.md` сразу в `docs/spec/03-dev-architecture.md`.
Затем запусти агента-критика **spec-critic** (Agent tool, subagent_type: `spec-critic`)
с заданием:

> Проверь слой 3 — `docs/spec/03-dev-architecture.md` (сверь со слоями 1 и 2).

Чек-лист проверки живёт в самом агенте (`agents/spec-critic.md` этого плагина).

### 8. Финал спеки

Это последний слой — после доработки покажи итог:

> Спека готова — все 3 слоя в `docs/spec/`:
> `01-functional-requirements.md` (ЧТО и для кого) · `02-tech-architecture.md` (НА ЧЁМ) ·
> `03-dev-architecture.md` (КАК запускать и проверять).
> Прочитай третий файл. Следующий шаг курса — дизайн и план разработки; спека — их основа.

Плюс резюме в 3–5 строк: сколько сценариев в петле проверки, что заменяем локально, открытые
вопросы. Никакой код и настройку окружения в этой сессии не начинай.

**Если в проекте уже есть план разработки** (`docs/tasks/`), добавь строку: петля проверки
изменилась, а задачи об этом не знают — предложи запустить `/create-dev-plan`, он сверит план
со спекой и поправит критерии задач. Сам план в этой сессии не трогай.

## Правила сжатия вывода

- Весь файл — **не длиннее ~1,5 страниц**; таблицы вместо прозы.
- Петля проверки — по одной строке на сценарий; сценарии берутся из фич слоя 1, не выдумываются.
- Без технических деталей настройки (какие образы, какие конфиги) — это следующий этап.
- **Финальный отчёт — по общему формату** (`skills/_shared/report-format.md` этого плагина):
  первой строкой итог, детали — в документ, в конце — блок «Что делать дальше».

без текста) — по умолчанию русский. Код и идентификаторы не переводятся.
