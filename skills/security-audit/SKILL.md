# Security Audit — весь проект перед выкладкой

## 📚 Объясни пользователю (перед началом, своими словами, 5–7 предложений)

Клиент — чужая территория: код, который исполняется у пользователя (JavaScript сайта в браузере,
распакованный бандл мобильного приложения, десктоп-сборка), видно и правится, а проверку «нажми,
если ты админ» или «у тебя оплачено» посетитель переписывает у себя за десять секунд — настоящая
защита бывает только на сервере. Ключи опаснее всего: по наблюдениям исследователей, выложенный
API-ключ находят боты за минуты, а больше половины утёкших ключей остаются рабочими годами —
поэтому засветившийся ключ **перевыпускают** у провайдера, а не просто стирают из кода. Отдельная
ловушка вайб-кодинга — базы с прямым доступом клиента: ИИ создаёт таблицы запросом, а не через
дашборд, и защита строк (RLS) к ним не прикручивается — база молча открыта миру. И деньги: лимит трат должен быть жёстким стоп-краном, а не уведомлением, иначе
дырявый эндпоинт или утёкший ключ приносят счёт на десятки тысяч. Этот скилл проходит проект по
чек-листу, **сам чинит в коде что может**, а остальное честно раскладывает: что он сделает за
тебя через CLI сервиса (с твоего разрешения), и что придётся сделать только тебе в кабинете
провайдера. Это защита **своего** проекта — финальная проверка перед тем, как его увидят чужие.

## Когда запускать

- Перед первой выкладкой и перед каждым заметным релизом.
- После крупной пачки ИИ-правок (новые таблицы, эндпоинты, работа с ключами).
- Периодически — свежим взглядом на уже задеплоенный проект.

## Порядок работы (скопируй чеклист в ответ и отмечай по ходу)

```
- [ ] 0. Ориентировка (чтение): стек и поверхности риска; какой чек-лист под стек; какие CLI авторизованы
- [ ] 1. Учебный блок: почему клиент публичен, ключи перевыпускают, защита строк базы, лимиты
- [ ] 2. Скан по чек-листу (секреты · доступ · деньги · конфигурация) — только детект
- [ ] 3. Разложить находки по трём группам: сам в коде · через CLI (с согласия) · только человек
- [ ] 4. Показать план тремя группами → ждать одобрения
- [ ] 5. Выполнить одобренное: сам-фиксы маленькими шагами; CLI-действия по одному с «да»; человеку — инструкции
- [ ] 6. Итог + доказательство закрытия; что перевыпустить; финальный ритуал /security-review
```

## Принцип: сначала ориентируйся, потом докладывай и чини

Проверки не берутся из привычки — они выводятся из технологий **этого** проекта. Настоящие
значения секретов **никогда** не выводи в отчёт, лог или чат — только место и тип («ключ OpenAI
в `src/...:NN`»). Это защита своего проекта, не пентест чужого.

### 0. Ориентировка — стек и поверхности риска (только чтение)

По манифесту, конфигам и коду определи (не по памяти) и собери чек-лист под стек:

- **клиентски-доступная база** (Supabase, Firebase…) — значит проверяем защиту строк и секретный
  ключ на клиенте; её нет — эти пункты не применяются;
- **платформа деплоя** — где живут переменные окружения и лимиты трат;
- **платные внешние API** в проекте — по каждому нужен жёсткий лимит трат;
- **префикс публичных переменных** у фреймворка (`NEXT_PUBLIC_`, `VITE_`, `EXPO_PUBLIC_`…) —
  что из него уезжает на клиент;
- **есть ли история git / публичный репозиторий** — нужен ли скан истории на секреты.

Заодно проверь, **какие CLI установлены и авторизованы** (`gh auth status`, `supabase`,
`vercel whoami` и подобные — по сервисам проекта): это решает, что попадёт во вторую группу
(сделаю через CLI), а что в третью (только человек).

### 1. Учебный блок

Проговори суть из блока «Объясни пользователю»: клиент публичен → защита на сервере; ключ
находят за минуты и он валиден годами → перевыпуск, не удаление; базы с прямым доступом клиента
ИИ создаёт без защиты строк (RLS); лимит трат = жёсткий стоп-кран.

### 2. Скан по чек-листу — только детект

Пройди проект по четырём категориям (конкретные проверки — под стек из шага 0):

- **Секреты.** Захардкоженные ключи, пароли, токены, строки подключения в коде. Секреты в
  **истории git** — прогони сканер секретов (важно для приватного репозитория: там пуш-защита
  бесплатно не работает). `.env` реально в `.gitignore`. Ни один секрет не назван публичным
  префиксом (`NEXT_PUBLIC_`/`VITE_`…).
- **Доступ к данным.** На клиент уходит только публичный ключ; секретный (например `service_role` /
  `sb_secret_…`) — исключительно на сервере. Если у стека база с прямым доступом клиента — защита
  строк (RLS) включена на **каждой** таблице открытой схемы. Каждый эндпоинт, отдающий данные по
  id, проверяет, что они принадлежат текущему пользователю. Нет мест, где доступ ограничен
  **только на клиенте** (спрятанная кнопка, редирект, условие в компоненте) без серверной проверки.
- **Деньги.** У каждого платного провайдера — жёсткий лимит трат (не только уведомление).
  Rate limiting на эндпоинтах, которые дёргают платный API. Формы и регистрация прикрыты от ботов.
- **Конфигурация.** В проде выключены debug-режим, подробные тексты ошибок и стектрейсы для
  посетителя. Нет тестовых/служебных страниц, «временных» админок без пароля, публичных
  эндпоинтов, которые должны быть закрыты.

### 3. Разложить находки по трём группам

- **① Сделаю сам (в коде).** Правки в репозитории: убрать хардкод-ключ из кода (и пометить его
  на перевыпуск), переименовать ошибочно-публичную переменную, увести секретный ключ на сервер,
  добавить **серверную** проверку владельца/прав, добавить rate limiting, выключить debug и
  подробные ошибки в проде, дописать `.env` в `.gitignore`.
- **② Могу через CLI — с твоего согласия.** То, что обычно «в кабинете», но выполнимо уже
  установленным и авторизованным CLI сервиса (из шага 0): например переменные окружения на
  платформе деплоя, перевыпуск ключа там, где провайдер даёт это через CLI/API, включение
  сканирования секретов в репозитории. Это **внешнее, часто необратимое действие** — предлагаю,
  но выполняю только по явному «да» на каждое.
- **③ Только ты (кабинет провайдера).** То, к чему нет доступа из командной строки или что
  требует твоего решения/аккаунта: жёсткие лимиты трат в биллинге платных API, перевыпуск
  утёкшего ключа у провайдера без CLI, спенд-капы платформы деплоя, ревью Security Advisor базы,
  решение «какие из публичных страниц должны быть публичными». По каждому: что, зачем, где
  (ссылка), что вернуть мне (например, какой ключ положить в переменные окружения).

Одна находка иногда бьётся на две группы: «убрать ключ из кода» (①) **и** «перевыпустить его
у провайдера» (② если есть CLI, иначе ③).

### 4. План → одобрение

Покажи план **тремя группами отдельным сообщением, которым ход заканчивается** (в некоторых
интерфейсах текст перед вызовом инструмента не виден — человек должен прочитать план до
одобрения). Жди «да»; скилл меняет код и дёргает внешние сервисы — без согласия не действуем.

### 5. Выполнить одобренное

- **Группа ①** — маленькими шагами, после каждого прогон проверок проекта: фикс закрывает дыру и
  **не ломает обычный путь пользователя**. Фиксы меняют поведение намеренно (закрывают доступ) — поэтому
  опирайся на тесты как на сеть (нет теста на этот участок → `test-audit` → `write-tests`,
  в идеале тест, доказывающий, что дыра закрыта: чужому теперь 401/403).
- **Группа ②** — по одному действию, каждое после явного «да»; перед вызовом убедись, что нужный
  CLI авторизован. Необратимое (перевыпуск ключа, смена прод-переменной) проговаривай отдельно.
- **Группа ③** — отдай человеку короткие пошаговые инструкции и дождись результата там, где без
  этого дальше нельзя (например, пока не перевыпущен утёкший ключ).

### 6. Итог и доказательство

- По закрытым пунктам — **наблюдаемое** доказательство, а не «поправил»: чужой пользователь на
  эндпоинте получает отказ (например 401/403); секретный ключ больше не уходит на клиент; сканер истории чист;
  тест на владельца зелёный. «Ошибок нет» доказательством не считается.
- Отдельным списком — **что перевыпустить** (засветившиеся ключи) и **что ждёт человека** (группа ③).
- Финальный ритуал-привычка: прогнать `/security-review` (ревью кода на инъекции/XSS/авторизацию)
  и глянуть задеплоенный сайт сторонним онлайн-сканером — свежим взглядом снаружи.

## Правила

- **Защита своего проекта**, авторизованная. Настоящие значения секретов не выводятся в отчёт,
  лог или чат — только место и тип.
- **Сначала детект, потом починка.** Ничего не правим и не дёргаем во внешних сервисах до плана
  и явного согласия.
- **Три группы.** Сам-в-коде · через-CLI-с-согласия · только-человек. Любое внешнее и необратимое
  действие (CLI, смена прод-настроек, перевыпуск ключа) — только после «да» на него.
- **Утёкший ключ перевыпускается**, а не стирается: удаление не спасает (история, форки, кэши,
  боты). Через CLI, если сервис это умеет и он авторизован; иначе — в группу «только ты».
- **Чек-лист — из стека проекта, не хардкод.** Скилл переносим: набор проверок зависит от
  технологий (клиентская база, платформа деплоя, платные API, публичный префикс переменных).
- **Сам-фиксы меняют поведение осознанно** (закрывают доступ) — план, одобрение, маленькие шаги,
  обычный путь пользователя остаётся зелёным; страховка — `test-audit` / `write-tests`.
- **Не решаю за человека, что должно быть публичным** — список публичных страниц/эндпоинтов
  показываю, решение оставляю ему.
- **Смотрю весь проект** — код, историю git, конфигурацию деплоя, — а не только текущий дифф;
  этим отличаюсь от `/security-review`, который остаётся финальным ритуалом.
- **Объясняй простыми словами** (клиент публичен, защита строк базы, лимит трат, перевыпуск ключа) —
  аудитория часто не программисты.
