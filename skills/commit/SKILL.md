# Коммит — сохранить работу понятными кусками

## 📚 Объясни пользователю (перед началом, своими словами, 4–6 предложений)

Коммит — точка сохранения в истории проекта. Ценность не в самом сохранении, а в том, что потом
можно прочитать историю и откатить одну правку, не задев остальные. Отсюда размер куска: если за
сессию сделаны три разные вещи и они уехали одним коммитом «работа за день» — откатить одну из них
уже нельзя, и история ничего не объясняет. Второе, что делает этот скилл, — смотрит на секреты
**до** коммита: git помнит всё, и ключ, попавший в историю, удалением файла не убирается — его
придётся перевыпускать. Отсюда порядок: сначала разобраться, что коммитим, потом проверить на
секреты, потом разрезать на группы, показать план — и только затем `git commit`.

## Порядок работы (скопируй чеклист в ответ и отмечай по ходу)

```
- [ ] 1. Учебный блок: зачем маленькие коммиты и почему секрет в истории — навсегда
- [ ] 2. Разведка (только чтение): что изменено и на какой ветке
- [ ] 3. Область: файлы этой сессии; есть грязные сверх них — спроси, коммитить ли их тоже
- [ ] 4. Стоп-кран: проверка на секреты и мусор — ДО первого git add
- [ ] 5. Группировка: несвязанные изменения — в разные коммиты
- [ ] 6. План → подтверждение → коммиты
- [ ] 7. Итог: что закоммичено, что осталось; push не делаем
```

### 2. Разведка — только чтение

```bash
git status --porcelain        # что грязно сейчас
git branch --show-current     # ветка
git diff HEAD -- <файлы>      # содержимое изменений (файлы перечисляй явно)
```

Проект живёт в одной ветке `main`: **новую ветку не создавай** (даже «чтобы не сломать») — коммить
в текущую.

### 3. Область — по умолчанию только эта сессия

Человек мог оставить прежние правки незаконченными нарочно. Поэтому по умолчанию коммитим
**только то, что появилось в этой сессии**, а остальное показываем и спрашиваем.

Как собрать список файлов сессии — два источника, оба нужны:

1. **Твои собственные правки**: файлы, которые ты сам менял через Edit/Write в этой сессии.
2. **Вычитание**: в контексте сессии есть снимок `gitStatus` на её старте. Грязные сейчас
   (`git status --porcelain`) **минус** грязные на старте = появившееся за сессию.

Второй источник один не годится: файл, который был грязным ещё до сессии и который ты потом
правил, вычитание не покажет — а он к работе относится. Такой файл (был грязным + ты его трогал)
бери, но отметь в плане: в нём есть и правки, сделанные до сессии.

**Есть ли что-то, кроме файлов сессии?** Посчитай: все грязные файлы минус файлы сессии.

- **Ничего не осталось** → вопрос не задавай, просто коммить сессию.
- **Что-то осталось** → эти файлы молча не бери. Покажи их списком (файл + одна строка, что в нём
  меняется — по `git diff`, чтобы человек вспомнил, что это) и спроси через AskUserQuestion,
  коммитить ли их тоже:

| Вариант | Что делает |
|---|---|
| **Только изменения сессии** *(Рекомендую)* | коммитим свою работу, остальное остаётся как было |
| Сессия + выбранные из остальных | человек называет, какие из прежних файлов взять |
| Все изменения | всё грязное уходит в коммиты |

Вопрос задай **один раз и до плана** — чтобы взятые файлы прошли проверку на секреты (шаг 4)
и попали в группировку (шаг 5) вместе с остальными.

Человек попросил прямо («закоммить всё») → вопрос не задавай. Коммитить нечего → скажи и стоп.

### 4. Стоп-кран — секреты и мусор

Проверка идёт **до** первого `git add`. Смотри и имена файлов, и содержимое диффа.

**Имена файлов — красный список:**

`.env`, `.env.local`, `.env.production` · `*.pem`, `*.key`, `*.p12`, `id_rsa` · `credentials.json`,
`serviceAccount*.json` · `.npmrc`, `.netrc`, `.aws/credentials` · дампы базы, `*.sqlite`

**Содержимое диффа — паттерны.** Новые файлы (`??` в статусе) в `git diff HEAD` **не попадают** —
а свежий `.env` или выгруженный ключ появляются именно как новый файл. Заяви их через `git add -N`
(заявка на добавление: файл становится виден диффу, содержимое в индекс не уходит) — иначе
проверка молча пропустит самое опасное:

```bash
git add -N <новые файлы>      # без этого новые файлы проверку не проходят
git diff HEAD -- <файлы> | grep -nEi 'sk-[a-z0-9]|sk-ant-|ghp_|github_pat_|xox[baprs]-|AKIA[0-9A-Z]{16}|AIza[0-9A-Za-z_-]{35}|BEGIN [A-Z ]*PRIVATE KEY|service_role|://[^/[:space:]:]+:[^/[:space:]@]+@|NEXT_PUBLIC_[A-Z_]*(SECRET|KEY|TOKEN|PASSWORD)'
```

**Находка — повод посмотреть, а не приговор.** Половина совпадений законна, и разобрать их —
часть учебного смысла:

| Совпало | Что это на самом деле |
|---|---|
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` — длинный JWT | норма: anon-ключ публичен по устройству Supabase (правило проекта разрешает только его) |
| `NEXT_PUBLIC_OPENAI_KEY`, `NEXT_PUBLIC_..._SECRET` | **стоп**: `NEXT_PUBLIC_` уезжает в браузер к каждому посетителю — секрета с таким префиксом не бывает |
| `OPENAI_API_KEY=sk-...` в `.env.example` | смотри значение: плейсхолдер (`sk-xxx`, `<your-key>`) — норма; настоящий ключ — стоп |
| `service_role` в коде сервера | норма, если ключ читается из `process.env`; стоп, если значение вписано в код |
| `password = "..."` в seed / фикстурах | обычно норма (тестовые пользователи), но покажи человеку строку |

Нашёл настоящий секрет: **не коммить**, покажи файл и строку, объясни и предложи починку —
значение в `.env.local` (он в `.gitignore`), в `.env.example` вместо него плейсхолдер, в коде —
чтение из `process.env` на сервере. Заодно проверь, что `.env.local` реально закрыт:
`git check-ignore -v .env.local`.

Секрет уже в истории (не в текущем диффе, а в прошлых коммитах): по правилу проекта
**ключ перевыпускают, а не стирают** — переписывание истории само по себе не спасает, ключ уже
утёк. Скажи это человеку и не бросайся чинить историю без его решения.

**Мусор** — в коммит не едет: `node_modules/`, `.next/`, `dist/`, `coverage/`, `*.log`,
`.DS_Store`, файлы из scratchpad/tmp. Попал в список — предложи дописать в `.gitignore`.
Файл тяжелее ~1 МБ или бинарник — спроси, нужен ли он в git.

### 5. Группировка — один коммит = одно изменение

Простой тест: **описал коммит одной строкой и в ней понадобилось «и» — режь на два.**
Второй тест: откат этого коммита оставляет проект в рабочем состоянии?

**Что едет вместе, а не отдельно:**
- `package.json` + `package-lock.json` — всегда в одном коммите;
- миграция базы + код, который на неё опирается — вместе, иначе между коммитами проект сломан;
- компонент + его типы + стили одной фичи — вместе.

Не дроби ради дробления: ≤3 файлов на одну тему → один коммит.

### 6. План → подтверждение → коммиты

Покажи компактный план: сколько файлов, сколько коммитов, по каждому — файлы (>5 файлов
сворачивай в «… и ещё N») и сообщение. Дождись подтверждения человека.

Дальше по каждой группе — точечное добавление, **никогда `git add .` и `git add -A`**: они заметут
и то, что человек не отдавал (в том числе .env и мусор — вся проверка шага 4 обесценится).

```bash
git add путь/к/файлу1 путь/к/файлу2
git commit -m "$(cat <<'EOF'
feat: Add size prop to Button component

Тело — только если тема не объясняет «зачем». Пиши почему, а не перечень файлов.
EOF
)"
git log --oneline -1          # наблюдаемый результат
```

Сообщение: **всегда на английском** (правило репозитория — общение на русском, git на английском),
формат `<type>: <description>`, повелительное наклонение, тема ≤70 символов.

| Тип | Когда |
|---|---|
| `feat:` | новая функциональность |
| `fix:` | починка ошибки |
| `refactor:` | код переставлен, поведение то же |
| `docs:` | документация, спека, правила |
| `chore:` | обвязка, зависимости, конфиги |
| `test:` | тесты |
| `style:` | оформление, стили, форматирование |

Трейлер `Co-Authored-By:` — как в истории репозитория (проверь `git log`: есть → ставь, нет → не
добавляй).

**Никогда без явной просьбы человека:** `--amend` (переписывает готовый коммит), `--no-verify`
(выключает хуки проверки), `git push`, `git reset`/`git checkout` по чужим правкам, новая ветка.

### 7. Итог

Одной сводкой: созданные коммиты (`git log --oneline -N`) и что осталось незакоммиченным.
`git push` не делай — правило проекта: одна ветка `main`, пуш только по явной просьбе.

## Ошибки и края

| Ситуация | Что делать |
|---|---|
| Коммитить нечего | «Изменений нет» и стоп |
| Только новые файлы | нормально: это добавления, но проверка секретов — через `git add -N` (шаг 4) |
| 50+ файлов | сначала покажи сводку по группам, спроси, продолжать ли |
| Хук проверки упал | покажи вывод, почини, сделай **новый** коммит (не `--amend`) |
| Хук сам переписал файлы | не амендь — скажи, что изменилось, и спроси, коммитить ли это отдельно |
| Конфликты слияния | покажи файлы, попроси человека разрешить, не коммить поверх |
